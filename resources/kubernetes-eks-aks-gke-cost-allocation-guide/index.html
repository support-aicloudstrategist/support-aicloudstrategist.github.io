Kubernetes cost allocation guide: mapping shared EKS, AKS & GKE spend to owners

Published: 2026-11-17 · Last reviewed: 2026-11-17 · Reviewed by AICloudStrategist FinOps Practice

Shared Kubernetes clusters are the #1 source of unallocated cloud bills—here is how to separate requested, idle, system, and cross-AZ spend cleanly.

In almost every multi-team AWS EKS, Azure AKS, or Google GKE estate, the cloud invoice shows EC2/VM nodes, EBS/Managed Disks, NAT Gateways, and cross-AZ data transfer—not product lines. Finance sees one giant cluster cost; product teams claim they only use a fraction of it; platform engineering gets stuck defending idle headroom.

Why naive namespace averaging fails

Splitting a USD 25,000/month cluster evenly across five teams punishes lean services and hides memory-overprovisioned workloads that force larger node groups. Credible Kubernetes cost ownership separates four distinct slices inside every cluster:

  • Workload-attributed spend: Pod CPU, memory, GPU, and persistent-volume requests (weighted by max of request vs actual usage) tied via mandatory namespace labels to a named product owner.
  • System & platform overhead: Ingress controllers, service mesh, Prometheus/logging agents, and CoreDNS—treated as a shared platform pool with an explicit split rule agreed by engineering and finance.
  • Cluster idle & headroom slack: Unallocated node capacity kept for burst scaling or left behind by oversized instance families—owned jointly by platform engineering with a clear target utilization band.
  • Out-of-cluster amplification: Cross-AZ pod chatter, NAT Gateway processing, and orphaned PVCs/load balancers left after Helm uninstalls.

Safe 30-day sequence before cluster rightsizing

  1. Enforce 3 namespace labels (`owner`, `product`, `environment`) and measure the unlabelled gap rather than guessing.
  2. Reclaim zero-risk orphans first (Act): unattached PVCs, idle non-prod preview namespaces, and unused load balancers.
  3. Rightsize noisy top-5 deployments (Investigate → Act): compare 14-day p95 CPU/memory usage against inflated pod requests before shrinking node pools.
  4. Hold on compute commitments (Hold) until node instance families and GPU node-pool schedules stabilize.
