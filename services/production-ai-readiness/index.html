Decision trigger

The system can demonstrate value, but the release evidence is incomplete.

This review is designed for founders, CTOs, product owners, risk leaders and operating teams preparing to give an AI system real responsibility. It tests whether the evidence supports that decision. The work does not assume that a successful demo proves reliability, security, authority or recoverability.

A useful starting point is a named system, intended users, business consequence, current release stage and the evidence already available. The review then separates what is observed from what the team believes, and turns missing evidence into owned actions.

Five decision domains

  1. Outcome and evaluation evidence
  2. Authority and human oversight
  3. Data, security and supplier boundaries
  4. Failure response, rollback and ownership
  5. Consumption, cost and operating viability
Method

Four stages create a defensible release record.

1. Frame the decision

Document the intended outcome, users, system boundary, material consequences and the exact decision due. A readiness review fails when it becomes an open-ended architecture assessment, so scope is tied to one release or responsibility change.

2. Inspect the evidence

Trace requirements into evaluations, test summaries, access controls, data flows, vendor dependencies, incident procedures and operating owners. Evidence is labelled current, stale, missing or not applicable.

3. Challenge failure and recovery

Review selected failure modes, unsupported answers, tool misuse, escalation, human override and rollback using agreed safe inputs. This is not a penetration test and does not replace specialist security assurance.

4. Decide and assign

Issue a release, remediate or hold recommendation with conditions, owners, evidence requests and a 30-day action plan. The recommendation states limitations and unresolved dependencies.

What this review does not claim.

It is not a certification, legal opinion, compliance attestation, penetration test, model-safety guarantee or substitute for the accountable system owner. It does not prove an AI system is safe under every condition. It creates an evidence-backed decision record for a defined release question.

Teams that already have an independent evaluation function, complete release evidence and named operating ownership may not need this service. Teams seeking a broad transformation program, continuous managed operations or regulated legal advice require a different scope or specialist partner.

Buyer questions

Questions the diagnostic is designed to answer.

How do we know the pilot is ready?

A pilot is not ready because it completed a demonstration. The decision needs agreed success and failure criteria, representative evaluation evidence, an accountable owner, human authority boundaries, incident response and a workable rollback path. The diagnostic identifies which evidence exists and which release conditions remain open.

What if the AI agent can take actions?

The review maps each tool, data source and consequential action to allowed scope, authentication, approval, logging, exception handling and human override. It tests the written boundary against available implementation evidence without requesting production credentials through the public intake.

Can this support procurement or board review?

The dossier is structured for decision-makers: the system boundary, evidence register, major gaps, accountable owners, conditions and limitations are explicit. It can support an internal review, but it does not replace a required audit, legal opinion or regulated certification.

What happens after a hold decision?

A hold is translated into an ordered remediation record. Each action includes the missing evidence, responsible owner, dependency and the check that would allow the decision to be reconsidered. This prevents a vague risk concern from becoming an indefinite project.
